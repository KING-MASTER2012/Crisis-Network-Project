# Changes: Apple phase I1 (the runtime) and a CI fix

Written without a Mac or a Swift compiler: **nothing here was compiled or run**. Likeliest first mismatches: the
spelling of the bindings' `CoreError` cases (isolated in `CoreFailure.swift`, see the comment there), Swift
concurrency warnings, and the Keychain on the unsigned iOS simulator test (`RuntimeAppTests`).

* **CI fix: "Permission denied".** A ZIP unpacked on Windows loses the executable bit of `scripts/*.sh`. The workflow
  now calls them with `bash`, `build-apple.sh` calls `bash scripts/gen-bindings.sh`, and the README says how to keep
  the bit in git (`git update-index --chmod=+x`). The CI jobs also run the tests of the new package.
* **New package `clients/apple/Packages/CrisisRuntime`** (the Swift counterpart of the Android `core:runtime`):
    * `NodeBootstrap` and `EncryptionPolicy`: interface check, storage directory, vault, open the database, hand out a
      `NodeRuntime`; `resetIdentity`. **Leftovers of an earlier install are discarded** (Keychain items outlive the app on

    * `NodeRuntime` (actor): the node's single owner; peer/packet events, calls and ticks run one after another; outputs
      routed to the `Transport` and to `notifications()`, `failures()`, `states()` (each call gets its own stream);
      timer rescheduled after every output; errors mapped to `CoreFailure`; a fatal one stops the runtime.
      The full API of the Android `NodeRuntime` (publish, contacts, trust, history, conversations, unread, stats).
    * `Transport` (`TransportEvent`) and `LoopbackNetwork`, same contract as Android (handles never reused, MTU enforced).
    * `SecretVault`, `SecretStore`, `KeychainSecretStore` (`AfterFirstUnlockThisDeviceOnly`, no iCloud, data protection
      keychain on iOS; the file keychain on macOS until I8), `NodeSecrets`. Never overwrites a secret it cannot read.
    * `StorageLayout`: `Application Support/Crisis`, excluded from backups, `completeUntilFirstUserAuthentication` on iOS.
    * `MonotonicWallClock` (+ `FileHighWaterStore`, `MemoryHighWaterStore`, `SystemClocks` on `mach_continuous_time`),
      `TimerPolicy`, `CoreFailure`.
    * `RuntimeSelfCheck`: clock, Keychain, bootstrap with restart and reinstall, two runtimes over the loopback.
* **Tests** (`swift test`, on the Mac, no Keychain needed): `TimerPolicyTests`, `MonotonicWallClockTests`,
  `SecretVaultTests`, `LoopbackNetworkTests`, `CoreFailureTests` (against errors the real core produces),
  `NodeRuntimeTests` (the exit test of I1: two runtimes with real cores, broadcast, private message and
  acknowledgement, link up and down, lifecycle, failure of the transport), `NodeBootstrapTests` (restart, reinstall,
  unreadable secrets, reset, encryption policies). The iOS test bundle runs `RuntimeSelfCheck` inside the app on the
  simulator (`Tests/iOS/RuntimeAppTests.swift`), which is where the real Keychain is exercised.
* **App**: the self-test screen now shows the core's and the runtime's report. `CrisisCore` got public initialisers for
  `SelfCheckStep` and `SelfCheckReport`. `project.yml` and the CI jobs know the new package.
* **Not in I1**: Bluetooth (I2, I3), real screens (I4+), the macOS data protection keychain (I8).

# Changes: Android phase A8 and Core phase C8 fix

Written without a Rust or Android toolchain: **nothing here was compiled or run**. Run
`cargo fmt --all && cargo test --workspace && cargo clippy --workspace --all-targets -- -D warnings`, then
`./gradlew test` and the instrumented tests (`./gradlew connectedAndroidTest`) on a phone.

## C8 fix (core)

* `core/crates/appcodec/tests/properties.rs`: `prop_assert!` turns the text of its argument into a format
  string, so the closure with `'\u{7F}'` and braces did not compile ("Invalid format string"). The check is
  now the function `is_allowed`.
* New FFI function `budget_status(used, limit)`: the byte counter of an already encoded payload (the announcement
  screen measures a payload, not a text). `count_bytes` uses it.

## A8 (Android)

* **The app uses the core's conventions.** `AnnouncementCodec`, `TextSanitizer`, `CardCodec`, `ByteBudget`
  (limits and `Count`), `Lifetimes`, `NicknameStore.normalize`, `Names.shortId` and `MessageStatus` keep their
  API, but their rules now come from the Rust core (`appcodec`) through UniFFI. The screens did not change.
  The JVM unit tests that exercised them moved to `app/src/androidTest` (the native library is only loaded on a
  device); the pure ones stay (`HexTest`). New `ConventionVectorsTest` runs the shared vectors
  `core/testdata/appcodec.json` against the app, and `DefaultLifetimesTest` took over the lifetime check of
  `NetworkSettingsTest`. The vectors reach the instrumented tests as resources (Variant API in `app/build.gradle.kts`).
* **Back buttons.** One component, `BackButton` (an arrow icon of 48 dp that mirrors in right-to-left
  languages; new drawable `ic_arrow_back`), at the start of the top bar of every screen that opens over the shell
  (`ScreenTopBar`); the title sits next to it and actions at the end. The "Back to settings" text button of the
  self-test screen became a normal top bar. In the introduction the four "Back" text buttons under the main
  button are gone: the arrow sits in the header next to the progress bar from the second step on (an empty
  space of the same size on the first). Strings `diag_back` and `onb_back` were removed.
* **BLE link profile 1.1** (`docs/src/protocol/ble-link.md`, rewritten: it now also describes the advertised
  token and the tie-break of A3, which it did not). New HELLO characteristic
  (`6f1d5a33-7c2e-4b8a-9d41-c3b5e0a7f2d6`, read and write): after the notifications are on, the client reads the
  server's 64-bit identifier and writes its own. Both ends of a link then know both identifiers; when a device
  holds two links to the same neighbour it keeps the one whose client has the lower identifier, and the client of
  the closed link leaves that address alone for 5 minutes (`duplicateCooldownMs`). The identifier rotates with the
  token. Needed for iOS, which cannot advertise a token, so two iPhones (or an iPhone and an Android phone) would
  otherwise always connect twice. A 1.0 neighbour has no HELLO and everything works as before.
  Code: `HelloValue`, `GattLinkEvent.PeerHello`, `setHello` on `GattConnector` and `GattServerPort`
  (default no-op), `BleTransport` (`onPeerHello`, `closeDuplicate`, `helloSource`), `AndroidGattClientLink`
  (new `Hello` step), `AndroidGattServer` (read and write handlers), diagnostic `DuplicateLink`,
  `BleStats.duplicateLinks`. Tests: `HelloValueTest`, `DuplicateLinkTest`, a case in `BleConfigTest`.
* Not tested on a phone: the hello exchange needs two real devices (an old and a new build is the useful pair,
  to prove that a 1.0 neighbour still works).

# Changes: Core phase C8 (app conventions in Rust)

Written without a Rust toolchain: **nothing here was compiled or run**. Run
`cargo test --workspace` and `cargo fmt --all && cargo clippy --workspace --all-targets -- -D warnings`
first (I could not run rustfmt, so formatting may need a pass). The Android client is untouched and keeps working: the interface version stays 2 because
the change is purely additive.

The small rules that every client must apply identically, until now written in Kotlin only
(`AnnouncementCodec`, `CardCodec`, `TextSanitizer`, `ByteBudget`, `Lifetimes`, `NicknameStore.normalize`,
`MessageStatus`, `Names.shortId`), now live in one new crate, so the Apple and Desktop clients
cannot drift from Android.

* **New crate `appcodec`** (pure functions, no I/O, depends only on `proto` for the limits):
  `clean` (control characters and bidirectional overrides), announcement payload with severity
  (`0x1E` + digit), contact-card text (`crisis:` + URL-safe base64, forgiving decoder with its own small
  base64), byte budgets (direct text limit = payload limit - 48), lifetime presets and units, nickname
  normalisation, delivery status, short node id.
* **FFI**: `conventions.rs` exports them (`sanitize_text`, `encode_announcement`, `decode_announcement`,
  `announcement_overhead`, `encode_card_text`, `decode_card_text`, `direct_byte_limit`,
  `announcement_byte_limit`, `count_bytes`, `lifetime_presets`, `lifetime_to_seconds`,
  `lifetime_is_valid`, `split_lifetime`, `normalize_nickname`, `short_node_id`,
  `message_delivery_status`, `convention_info`) with the types `AnnouncementSeverity`, `LifetimeUnit`,
  `DeliveryStatus`, `DecodedAnnouncement`, `ByteCount`, `LifetimeParts` and `ConventionInfo`.
  Lifetimes are `i64` seconds; a negative value counts as zero.
* **Shared test vectors**: `core/testdata/appcodec.json`, produced by an independent implementation of
  the Android rules (not by the Rust code). The Rust tests read it; a client with its own copy of a rule
  can run the same file.
* **Tests**: unit tests in every module, `tests/vectors.rs`, property tests (`tests/properties.rs`:
  round trips, idempotence, no panics) and a fuzz target `appcodec_inputs`.

Known differences from the Kotlin code (none changes what is sent on the wire or what another phone
shows): nicknames are cut at 40 Unicode scalar values (Kotlin cuts at 40 UTF-16 units, which can split an
emoji); byte limits saturate at zero instead of going negative; invalid UTF-8 is replaced the way
Rust's `from_utf8_lossy` does, which can differ from Java for some malformed sequences.

Files: new `core/crates/appcodec/` (`Cargo.toml`, `src/{lib,sanitize,announcement,card,base64,budget,lifetime,names,nickname,status}.rs`,
`tests/{vectors,properties}.rs`), `core/crates/ffi/src/conventions.rs`, `core/testdata/{appcodec.json,README.md}`,
`core/fuzz/fuzz_targets/appcodec_inputs.rs`; changed `Cargo.toml`, `Cargo.lock` (by hand: one new package),
`core/crates/ffi/{Cargo.toml,src/lib.rs,src/version.rs}`, `core/fuzz/Cargo.toml`, `README.md`.

Next: Android can switch to the Rust functions later (optional, it would be a small A8 change);
the Apple client (I5) uses them from the start.

# Changes: Android phase A5 (contacts, chats, announcements)

Written without an Android toolchain: **nothing here was compiled, run or tested on a device**. Build
(`./gradlew :app:assembleDebug :app:testDebugUnitTest`), then try it with two phones. Needs the C7
change below (core API version 2 and regenerated bindings).

* **Contacts.** Show your own card as a QR code (and copy or share it as text), scan another phone's
  QR code, or enter a card as text. Adding a card shows the safety number to compare and asks for a
  nickname. A contact detail screen compares safety numbers, marks a contact verified (or removes it)
  and blocks or unblocks. A card scanned while the mesh is off is kept and added when the node runs.
* **Chats.** List of conversations (preview, time, unread count), the chat screen with backward
  paging, a "new messages" line, "Published" / "Delivered" under sent messages, a UTF-8 byte counter
  against the 976-byte limit of a private message, and a choice of contact for a new message.
* **Announcements.** Feed (newest first, backward paging, unread line), composer with a byte counter,
  importance (normal / important / emergency, shown with a word and a colour), and a lifetime from
  1 second to 7 days (presets and a custom value). Important and emergency ones ask for confirmation.
* **Unread badges** on the Chats and Announcements destinations; read state lives in the core (C7).
* **Convention to share with the other clients:** an important or emergency announcement starts its
  payload with the bytes `0x1E` and the ASCII digit `1` or `2`, then the UTF-8 text; a normal one is
  plain text (see `AnnouncementCodec`). Text from other phones is cleaned of control characters and
  bidirectional override characters before it is shown.
* **QR without Google Play services:** ZXing (plain Java) draws and reads the codes, CameraX delivers
  the frames. This replaces the bundled ML Kit model of the plan: no native library is added, so
  nothing new needs the 16 KB alignment check. A contact card is tiny (QR version 8, 49 modules).
  Dependencies added: `com.google.zxing:core:3.5.3` and `androidx.camera:*:1.4.2`; check for newer versions.
* New permission `CAMERA` (and optional camera features in the manifest); the camera is asked for
  only on the scan screen, with the reason first.
* `NodeRuntime` gained `conversations`, `conversationHistory`, `markConversationRead`, `unreadCounts`;
  `MeshController.dataVersion` tells screens that messages changed; the contact card text is stored
  with the identity (`UiPreferences`) so that the QR code is shown without opening the node.
* Known limits, left for A6/A7: messages can only be read and sent while the mesh runs (the node is
  opened by the foreground service only); nicknames are plain app-private preferences (not encrypted);
  no notifications for incoming messages yet (A6); the card is shown as text and QR only.
* Tests (JVM): card codec and QR round trip, announcement codec and sanitizing, limits and lifetimes,
  nicknames, hex, overlay stack.

# Changes: core phase C7 (conversations: paging, unread, delivery state)

Written without a Rust toolchain: **the Rust sources were not compiled or run here**. Run
`cargo fmt --all`, `cargo clippy --workspace --all-targets -- -D warnings` and
`cargo test --workspace`, then rebuild the Android bindings (`gen-bindings.sh`).

* Storage schema **version 3** (migration is automatic, existing data is kept): indexes for
  per-conversation queries, `message_notes` (removed together with its message by a foreign key)
  and `read_marks` (one per conversation; the announcements use the single byte `0` as scope).
* `storage`: `conversation_messages` (backward paging, oldest first within a page, `more_before`),
  `conversations` (list with last position, message count, unread), `read_mark` / `mark_read`
  (never moves backwards), `unread_counts`, `set_plaintext` / `mark_delivered` / `note`.
* `engine`: `conversations`, `conversation`, `mark_read`, `unread_counts`. `HistoryEntry` gained
  `delivered_at_ms`. `Engine::handle` records `Notification::Delivered` in the store.
* **Behaviour change:** the text of a direct message the user sent is now kept next to the stored
  (sealed) message, so the history and the chat show it. The copy lives in the same database,
  under the same at-rest encryption, and is deleted with the message when it expires, is evicted
  or is deleted. Messages sent before this version stay unreadable on the sender's side. A crash
  between storing a message and storing its text leaves that one message without text.
* `ffi`: new `conversations`, `conversation_history`, `mark_conversation_read`, `unread_counts`;
  new types `ConversationRef` (`Announcements` / `Direct { peer }`), `ConversationInfo`,
  `ConversationPageInfo`, `UnreadInfo`; `HistoryItem.delivered_at_ms`.
  **`FFI_API_VERSION` is now 2** (the Android `EXPECTED_FFI_API_VERSION` follows).
* Tests: `storage/tests/conversations.rs`, migration tests for version 3 (the old tests now build on
  the real migration list), new engine and FFI end-to-end tests; the engine test that expected a
  sealed outgoing body now expects the text.
* Not changed: Kotlin wrappers for the new calls (phase A5), the CLI, the protocol and the wire format.

## New crate `ffi` (library `crisis_core`)

A thin, versioned [UniFFI](https://mozilla.github.io/uniffi-rs/) layer over `engine`, for Kotlin
(Android) and Swift (iOS, macOS). Desktop (Tauri) can link the crate from Rust directly. It uses
UniFFI's proc-macro mode, so there is no UDL file.

* `CrisisNode` (object, thread-safe): `open` / `in_memory`; `node_id`, `contact_card`, `safety_number`;
  events `peer_seen`, `peer_lost`, `packet_received`, `tick` (each returns a `CoreOutput`);
  `publish_broadcast[_with_lifetime]`, `publish_direct`, `publish_direct_to_card`;
  `add_contact`, `contacts`, `set_trust`; `history`, `connected_peers`, `stats`.
* Free functions: `default_settings`, `generate_seed`, `generate_database_key`,
  `inspect_contact_card`, `core_info`, `ffi_api_version`, `require_api_version`.
* Data: ids and keys are byte arrays; neighbours are `u64` handles chosen by the transport;
  `CoreOutput { transport, notifications, next_timer_ms }` carries everything the platform has
  to do. Bluetooth, the clock and the secure key store stay on the platform side.
* `CoreError` is a stable error enum (for example `WrongKeyOrNotADatabase`,
  `EncryptionUnavailable`, `SchemaTooNew`, `UnknownContact`, `InvalidContactCard`,
  `VersionMismatch`); `detail` texts are for logs only. A key given to a build without SQLCipher
  fails instead of silently storing unencrypted data.
* The identity seed and the database key are zeroized after use on the Rust side.

## Versioning

* `FFI_API_VERSION` (now 1): bump on every incompatible change of the exported interface.
  Applications call `require_api_version(EXPECTED)` once at start-up.
* `core_info()` reports the crate version, API version, wire protocol version, database schema
  version (new `storage::schema_version()`), minimum link MTU and protocol limits.
* UniFFI also checks at load time that bindings and native library match.

## Tooling

* `ffi` has its own `[lints]` table: `unsafe_code = "allow"` because UniFFI's generated code needs
  it; nothing written by hand uses `unsafe`.
* `scripts/gen-bindings.sh` / `.ps1`: generate Kotlin and Swift bindings into `target/bindings`.
  They use an unstripped **debug** build (the release profile strips the symbols UniFFI reads);
  the generated code works with the release libraries of every platform.
* CI: new `bindings` job generates and uploads the bindings.
* Workspace `Cargo.toml`: comment updated. `storage` gets `schema_version()`.

## Tests

* `ffi/tests/end_to_end.rs`: two nodes wired through byte packets: direct message delivered,
  decrypted and acknowledged; broadcast; contacts and trust; bad input; settings; restart with the
  same database; history paging; secret generation; version check; use from several threads.
* Unit tests for error mapping, type conversions and versioning.
